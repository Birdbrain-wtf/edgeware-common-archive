Applying Meta Transactions on Edgeware  :

Building a relayer infrastructure involves building components that handle different aspects of a blockchain transaction which involves creating the blockchain transaction in a correct format, signing the transaction with correct relayer so it doesn’t get stuck on network, choosing the right gasPrice for the transaction, handling long pending transactions and keeping the latency minimum while relaying the transaction. 
									
1. _Scalable Relayer Engine_


The core component of relayer infrastructure is a relayer engine that is auto-scalable, secure and provides low latency and high throughput while relaying the blockchain transactions. Following modules are required to create a scalable and efficient relayer engine:

- Relayer Manager		

	
This module is responsible for managing multiple relayers being run in parallel. It takes care of balances in multiple relayers and if any relayer is running low on balance then it auto funds the relayer from one main account. If there are a lot of transactions being queued in a relayer, it makes the relayer inactive and lets the transactions flow out of the queue before making it active again.It needs to make sure that the correct and optimized relayer is being chosen for an incoming transaction.	
			
- Transaction Listener			

	
The system needs to keep track of the state of each transaction being relayed so this module takes care of keeping the system up to date regarding the state of each transaction relayed by the system.
This will be useful to know whether a transaction is pending for a long period of time in the mempool and if an action is needed to make the transaction confirmed.		
			
- Internal Nonce Tracker			

In order to keep the latency to minimum we need to avoid making rpc calls to the blockchain for every read operation as a single rpc call could be anywhere between 500ms - 1sec response time.
Also while relaying the transaction from multiple relayers each transaction nonce has to be in correct order. So internal nonce tracker makes sure it returns a correct nonce for each relayer whenever the relayer is chosen to relay a given transaction.	
	
- Long Pending Transaction Handler			

The gas prices are not fixed and are driven by the market and miners. So even if the gasPrice was chosen very precisely it could be the case that while relaying the transaction gas prices can increase and the transaction would result in the mempool for a long time. This module makes sure that no transaction is in the memory pool for very long and if it happens it replaces the transaction with a higher gas price.
- Gas Optimisation 	

The main focus of relayer infrastructure is not just to relay the transaction as it is. We can leverage the infrastructure to optimize the gas fee of the transactions as it relays multiple transactions. Other gas saving methods can be used as per the protocol. This would need more research.

Biconomy will be deploying a set of smart contracts that will enable different meta transaction use cases on Edgeware like gasless transactions, paying gas fee in other tokens, Token transfer handler that’ll enable use cases like approve and transferFrom for ERC20 standard like tokens.

- Nodes


Biconomy needs to be connected to the blockchain in order to do read and write calls. Biconomy needs to connect to either multiple nodes hosted by others or if no node service provides are available, Biconomy needs to run blockchain specific nodes also.

- _Developer Dashboard_


Developer dashboard is required for granular control on meta transaction and showing statistics for developers to do analytics on top of the usage data. Developers will have an option to put limits on meta transaction usage per dapp, per method and per user.
Limits can be put on the basis of gas usage or number of transactions.
