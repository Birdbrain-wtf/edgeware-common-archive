## Takeaways

- The Tezos Babylon Upgrade, implemented on October 18, 2019, marked the first time a protocol has successfully automatically implemented two upgrades, and the first time two independent developer teams worked together to implement a proposal.
- Notable changes include introducing quorum caps, a new consensus algorithm, and changes to the coding language that allow for improved smart contract interactions
- Developers of the upgrade have reflected that increased documentation, more time for community testing and feedback, and a faster voting period could have facilitated a better upgrade process

-----

### A First for On-chain Governance: the 2nd Update to the Tezos Protocol

The Babylon Upgrade, implemented on October 18, 2019, was the second amendment to the Tezos protocol via the Tezos governance mechanism. The upgrade marked the first time a protocol has successfully automatically implemented two upgrades, which were approved by the community and initiated with the governance system (Tezos Foundation). 

The Babylon Upgrade was developed by TQ Tezos, Nomadic Labs, and Cryptium Labs (Tezos Foundation). According to a post from Cryptium Labs’ founder Awa Sun Yin, the upgrade, which is also known as protocol 005 and was successfully activated on block 655361, marks another first: the first time two independent developer teams worked together to implement a proposal. 

### Babylon's Changes

Cryptium Labs lists the following successful changes under the Babylon Upgrade: 

- Addition of quorum caps
- Transition to Emmy+
- Making implicit accounts delegatable
- Implementing multiple big_maps and entrypoints
- Adding spam prevention for proposals (Yin)

Quorum caps will be at 20 and 70 percent, in order to ensure enough participation, but also hopefully avoid capture of votes by any entity (McKenzie). 

+Emmy is an improved consensus algorithm that uses probabilistic assumptions and game theory to create a consensus algorithm that, taking some ideas from Tendermint, does not have an obligation to endorse a block, but instead makes it theoretically advantageous (McKenzie).

Making implicit accounts delegatable is to avoid needing to make an originated account (without any script) to delegate - which will allow originated accounts to be solely focused on smart contracts (McKenzie). 

Changes to the stack-based language used in Tezos, Michelson, allow for the big maps and entrypoints changes, which will provide more information for a contract, make it easier to call only the relevant part of a contract, and allow developers easier access to different depths of contract code (McKenzie). 

### A Big Step Up From Athens 

The first upgrade to the Tezos network was Athens, which took effect in May of 2019. There were originally two proposals, put forth by Nomadic Labs in February. One was to increase the gas limit *and* reduce the “roll size,” or the amount of tez needed to participate in governance. The second option only increased the gas limit, but the community chose the option that implemented both changes (Arluck).  

When a proposal is made for Tezos, it is first voted on to see if it should enter an exploratory period. Then, should it be approved by the community, the proposed changes enter a 48-hour test-fork period before full integration (Arluck). 

Yin calls Babylon a huge step up from Athens, in that it went far beyond showing that live upgrades could work, towards actually making large, meaningful improvements to the codebase. 

### Looking Back: How to Improve

Yin does acknowledge that many development steps were rushed, which led to a lack of clear communication with the community. Yin suggested that, in the future, a list of specific features to work on should be compiled early, receive community feedback, and not be expanded in order to allow for a more concrete and realistic timeline projection. Much of Yin’s retrospective on the upgrade focused on getting better feedback from developers (including allowing for more experimentation opportunities), providing better documentation, and not moving hastily.    

A good example of this was their issue with big maps, a feature they felt pressured to provide for smart contract authors, but found a bug in during the test period. Instead of proposing a new, revised version of the Bablyon upgrade, which would have added three months to the process because of voting period limitations, the team left the proposed version with the bugged big map and offered a parallel update to Tezos nodes that would activate a fixed version of the upgrade, should the original, un-patched version be patched (Yin). While the Cryptium Labs team asserted that this hotfix worked fine, they allowed that it was not an optimal process. 

There was also a bug found in the new consensus algorithm, +Emmy, which made block rewards different than expected, as well as issues with K1+ accounts (Yin). The Cryptium Labs team hopes that in the future, better tools like block explorers can be used to allow people to better inspect the net and avoid these sorts of bugs. Yin also iterated that the process has also shown the need to allow for shorter voting procedures, in order to allow multiple improved proposals to be put forth. 

Yin's reflections respond well to current thought within the Tezos community. As one Reddit poster iterated, there were clearly bugs - the poster noted the K1+ and block reward issues in particular, and called for stronger testing in the future. They also pointed out the multiple improved proposals submitted during one voting round and suggested in the future that these should be ironed out before submission. 

Lastly, the Redditter strongly suggested clearer documentation and communication, especially for the “lay people” who are simply holding and not deeply involved in the technical side of the protocol. Notably, the user suggests that more average, non-technical users should be given more opportunities to participate in the testing process, suggesting that the community believes it should be more focused on less technical users (TezzieTuesday). 

Tezos is still looking forward to introducing a faucet to help send the Tezos native currency, tez (XTZ), to developers looking to test tools and smart contracts on the protocol. They plan to launch the faucet tool sometime in November (Tezos Foundation).
