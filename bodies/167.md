It's the first week of December and we're happy to share some good news! Over the past month of November, we've been working hard ironing out issues that we faced launching Edgeware the first go-around. Launching blockchains is not easy, and we hit some obstacles in the road that we have smoothed out.

1. Firstly, we have addressed the balance distribution issue that was mistakenly included in the initial go around. Edgeware distributions are now based on multiplicative bonuses as we communicated on all our social channels. All your balances should be ameliorated in the newest testnet which is currently running!
2. In addition, we have continued to upgrade the Edgeware node to feature-parity with substrate's core logic. This includes many fixes to nodes being slashed that we were facing. This does not mean we won't face new issues as the software is still very new and experimental, but it is a step in the right direction.
3. We have also added our own contributions to the substrate codebase, namely to improve the Aura module. Previously, Edgeware faced issues processing upgrades due to failing to process a runtime upgrade in the time given for each slot. Now, however, there is a linearly-increasing delay when failing to process a runtime upgrade. 

In addition to these updates, we also successfully held the first Edgeware Community Call on November 22nd! The details can be found here: [https://commonwealth.im/edgeware/proposal/discussion/149-edgeware-community-call-20191120-notes](https://commonwealth.im/edgeware/proposal/discussion/149-edgeware-community-call-20191120-notes). In this call we discussed improvement proposals, validating, and other changes to the protocol. There are some new changes since then that we will also outline here since we've continued to upgrade at a fast pace.

In the call we described our hopes to stick with many of the design decisions that had previously, such as using only 3 keypairs for validators. At the moment, we have decided to adopt as much of substrate's logic that we found useful and will be using 4 keypairs for Edgeware validating. These are:

1. Aura keys (ed25519)
2. Grandpa keys (ed25519)
3. ImOnline keys (ed25519)
4. AuthorityDiscovery keys (sr25519)

This means you will need to manage some number of hot keys on your validators, including the new authority discovery keypairs, which lets authorities discover one other.

As for Edgeware's plans and future work, we've had a number of fruitful discussions on improvements we can make to the protocol. We have made strides pushing our grant proposal for a zero-knowledge identity system forward with the Web3 Foundation and have also had a number of fruitful discussions with the KILT Protocol team as to how we can mutually benefit from a shared set of zero-knowledge tools. This project is now actively being developed and we are always looking for interested parties who want to help out.

During the community call, we proposed a number of upgrades for Edgeware. One, in particular, is including the EVM module into the Edgeware runtime once it is vetted. This would enable Edgeware to support a variety of different smart contract execution engines, gaining compatibility with Ethereum's contracts. This is super exciting as it would allow us to bridge years of work done in the Ethereum ecosystem to Edgeware and the substrate ecosystem.

Stay tuned for more updates to a new testnet and mainnet launch!
