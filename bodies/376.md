# Addressing finality issues

As it stands, the Edgeware node has been having some issues with validators not voting in the finalization process, leading finalization to stall and eventually triggering forced GRANDPA set updates. Not long ago with the help of [Andre Silva](https://github.com/andresilva) we merged in some changes to the GRANDPA service worker, and turned off forced finality changes to the Edgeware runtime. These changes will make their way into the first Edgeware runtime upgrade.

For technical details, please refer to:

1. [Disable GRANDPA finality fallback](https://github.com/hicommonwealth/edgeware-node/pull/141)
2. [Disable GRANDPA observer](https://github.com/hicommonwealth/edgeware-node/pull/140)

In addition to that, we've been actively following Substrate's work and the more stabler `polkadot-master` branch to peg our Edgeware updates to. We currently have an active PR up that addresses the new changes. In this update which will be the first upgrade freeze, we are cleaning up the following issues:

1. Crashes in the v1.0.1 node due to inproper time arithmetic
2. Memory leaks in the Edgeware node

# Staking issues

As most people in the community know, Edgeware experienced a [slashing event](https://polkascan.io/pre/edgeware/event?module=staking&event=Slash&page=1) at block 126,200. A majority of Staking Facilities sentry nodes stalled and dropped from the network due to a "too many open files" issue. What causes this is usually an improper `ulimit` parameter. Though, we can speculate that the node is creating many temp files to cause such issues.

Staking Facilities' postmortem of their issues can be found [here](https://medium.com/@stakingfac/postmortem-2020-02-25-edgeware-validator-outage-645a728dbd2f). While the slashing events are unfortunate, Edgeware is an open-governed system, and anyone may submit treasury proposals to reimburse slashing events.

Specific causes and remedies to this issue:

1. An improper system `ulimit` parameter.
2. An improper `systemd` `ulimit` parameter. The default for running `systemd` services on our machines was `4096`.

These parameters can usually be set much higher and there's an option you can specify as `unlimited`.

Additionally, we recommend using more complex monitoring criteria for nodes. Some issues that arise due to the Edgeware node or one's own setup may not always cause direct crashes of the node, but instead cause the node to stall as above.

We recommend adding to your monitoring solution checks that ensure your node has peers, is at the latest block, and is updating that latest block every 6-18 seconds. We have a [guide](https://github.com/hicommonwealth/edgeware-node/wiki/Setting-up-monitoring) in the Edgeware node wiki for using `nodeup` in addition to `monit` to achieve some of these criteria. (If you are using nodeup, please note that it will need to be manually updated around the time of runtime upgrades, in order to remain compatible with the latest API.)

Longer term, we expect there will be an upstream fix to address issues with over-provisioning of file descriptors. In the meantime, we recommend taking all the steps above to reduce the likelihood that your node goes offline.

We are always actively monitoring changes within the upstream Substrate branch to continue alleviating these issues and will work to keep the community updates as best we can.

# The first upgrade

Edgeware is an upgradable system as we all know, and we've been planning the first runtime upgrade since we launched. The process for upgrading the system follows that of any other democracy vote, in that an individual can propose a runtime upgrade and it will pass if it garners enough support.

First, our timeline for processing the upgrade:

1. First, we will prepare the runtime upgrade and run it on local testnets before merging in to the latest `edgeware-node` master branch on Github.
2. Second, we will run this upgrade on the Berlin testnet and let the chain run for 14-21 days to assess any issues that arise, whether these be node crashes or finality issues or other problems.
3. Finally, we will propose the upgrade in a democracy vote, with hashes and verifiable data to ensure the upgrade reflects the latest code in the master branch of `edgeware-node`.

## What will this upgrade contain?

1. We may need to run a custom upgrade to catch up to the latest version of Substrate, to migrate user accounts from the `balances` to the `system` module. Although, the migration code in Substrate continues to change and may support the migration we need.
  - Edgeware launched with the `balances` and `vesting` module as separate modules. After the launch of Edgeware however, another change was made to the storage of user account balances in Substrate, and user accounts and their balances are now managed under the `system` module and not the `balances` module.
2. We will be turning off forced GRANDPA authority set changes in an attempt to improve finality reliability.
  - This should bring us into sync with Kusama, which has not faced any issues with block finalization.
3. We will remove the nickname module from the Edgeware runtime.
  - As it stands, the identity module proves much more valuable functionality than the nickname module. Since after all, one can be used in place of the other while the reverse is not true.
4. We will amend the session lengths which are currently 10 minutes long to be 1 hour long. This will in turn increase the era lengths and the bonding duration
  - 1 hour sessions
  - 6 hour eras
  - 28 era bonding durations
5. We will include changes to the runtime that bring us up to par with the respective module changes in the upstream Substrate master branch.
