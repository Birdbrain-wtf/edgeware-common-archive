## Problem:    
During the process of upgrading edgeware’s network a lot of holes where hit in the road, one of them was dealing with edgeware’s out of date testing suit. Flipchan now propose a plan for a new tool to make running tests before and after a runtime upgrade easier.
 
## Goal:    
Provide more documentation and a stable testing suit that makes it easy and straight forward for developers to test runtime upgrade and pallet functionality 
 
## Introduction:   
Flipchan has previously been tasked to perform a massive runtime upgrade, The upgrade was very complex and a lot of holes were found in the road. But thanks to this experience flipchan has gotten a clear landscape of how Edgeware’s chains operated and wishes to spend his time on:     

#### 1: Upgrading edgeware’s current testing kit(https://github.com/hicommonwealth/edgeware-state-tester).  
Right now the tests for Edgeware are out of date, the process of porting them to a better and more feature rich implementation has been started by flipchan()
 
 
#### 2: Documentation     
There is currently a giant lack of documentation in the substrate space for performing Runtime upgrades and doing proper testing of the chain. Therefor two guides are going to be added to Edgeware’s wiki page. The first detailed guide will be about what runtime upgrades are, how the state changes, why we need migrations and how they work as well as how to perform them. The second guide will focus 110% on testing 
 
#### 3: Port over edgeware’s tests to a scalable Rust implementation     
The new tool  will be introduced for testing before and after functionality of runtime upgrade, this tool will be called “uptest”. As the last step, all current tests are written in the high level scripting language Typescript. Uptest will allow developer to easier write before and after upgrade tests for runtime upgrades. The first iteration will have all the functionality that has been added into the upgraded state tester. This tool will support metadata 14 and later(which we are currently upgrading too) and will be based on Parities new rust framework “Subxt”(https://github.com/paritytech/subxt). The goal of this tool will be to make it easier for developers and provide a native rust testing framework for Edgeware.
 
 
#### Problem:     
During the upgrade process of edgeware, a lot of tools and frameworks was tried, the current toolset that is available is either old and unmaintained(like the fork-off tool). As a pure community driven DAO that Edgeware, we do not want the process of upgrading the chain to be hard, poorly documented and difficult to test. This proposals allows several important upgrades to Edgeware’s testing implementation, allowing tests to be performed in a much cleaner and simpler way.
 
 
#### Research done on testing:     
As a result of the last couple months of work, flipchan has tested a large chunk of tools that are available to the substrate ecosystem. Including: subalfred, fork-off-substrate, halva, Acala’s testing suit and Picasso’s simnode. The current toolbox in the substrate ecosystem does not allow you to simply write before and after tests.

After this proposal has been fulfilled and fully delivered, Flipchan wishes to take on the role of starting Edgeware’s benchmarking journey.
 
Benchmarking will allow Edgeware to have correct transaction fees based on properly calculated numbers instead of the default ones. 
 
### Why is benchmarking important for substrate based chains?
 
What benchmarking means in this context is: dry-running on-chains functions to determine the time(weight) it takes for the function to run from finish to end. This number is used as the transaction fee. So benchmarking is making sure we have the correct transaction fees. If we have to low transactions fees the chain risks getting flooded with bad transactions, causing overloads and nodes to crash. Every time a user makes a transaction, that user pays for the computation power and the storage needed for the transaction. We need to be able to pre calculate estimated transaction fee’s in order not to over charge users and at the same time protect the network from spam and having the correct delay for each transaction. 
 
 
 
Transactions fees are based on the execution time of the functions and benchmarking is the art of dry-running all functions.
