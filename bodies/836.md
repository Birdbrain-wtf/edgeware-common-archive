# Objective of this proposal

**[DeepDAO](https://deepdao.io) ([https://deepdao.io](https://deepdao.io)) is the #1 discovery platform for DAOs and governance systems, centered on analytics and information gathering. Our main dashboard enumerates and ranks DAOs on several key metrics such as membership and assets under management (AUM). **

**DeepDAO data is being used by major research firms (Delphi Digital, Messari), journalists, VCs, and DAOists across the crypto ecosystem. All DAOs on our platform currently run on Ethereum or xDAI, and we are expanding our coverage to other chains and governance platforms as well. **

**DeepDAO is interested in adding Edgeware to DeepDAO as part of our Substrate organizations integration, and would like to propose an Integration of Edgeware data via an API. This will provide strong exposure to Edgeware in the Ethereum ecosystem, and will allow both communities to expand cooperation and integration of products and ideas. **

## **DeepDAO responsibilities **
1. DeepDAO will curate the DeepDAO integration proposal, select the API provider and monitor its progress. 
2. DeepDAO will integrate the API and list, rank, and analyze Edgeware on DeepDAO’s dashboard.
3. DeepDAO will be responsible for monitoring changes that would require a new, or different API structure for gathering the Edgeware data required for listing on DeepDAO’s dashboard. 


## **Timeline**
1. API Delivery: TBD after conversations with potential API providers. 
2. DeepDAO integration: 1 month from deployment of API’s final version. 


## **Cost**
1. API Development: TBD after conversations with potential API providers.

## **API requirements for DeepDAO integration with Edgeware **

As part of this proposal DeepDAO will integrate governance and financial data from Edgeware into DeepDAO and will list, rank and analyze Edgeware as part of our DAO ecosystem. 

If necessary DeepDAO will curate the integration process, and will be responsible for finding an API provider. It’d be great if Edgeware is able to take care of the API internally.

1. The API will cover governance and financial information on Edgeware, both historical and current. 


1. **Data requirements:**
2. **Members.** All organization’s members. A member is defined as an address with voting power in the organization. (Note on voting power: in Democracy vote is by number of tokens; in Council one person one vote).  
3. Address 
4. Id (if different than address)
5. Created at 
6. Voting power - current, and historical
7. Shares (if different than voting power) 
8. Is active (if different than zero balance) 
9. Other, platform specific information

 
1. **Proposals.** All organization’s proposals, from the beginning until present time.
2. Proposal title 
3. Proposal description 
4. Proposal type (democracy, council, technical, other) 
5. Proposer id (address) 
6. Curator (if applicable)  
7. Payee (if applicable, the person, or entity involved in executing the proposal and getting the funding) 
8. Status - ongoing, pending, accepted, paid out.
9. Started and ongoing
10. Rejected by democracy
11. Accepted by democracy and in execution queue
12. Rejected by council 
13. Executed 
14. Proposal creation time
15. Proposal end time 


1. **Votes. **All organization’s votes 
2. Vote id 
3. Voter address 
4. Voter id (if different than address) 
5. Vote creation time 
6. Vote decision (yes, no, other) 
7. Vote strength (in democracy by tokens, in council 1 person 1 vote) 
8. Vote timelock (only for democracy) 


1. **Financial information**
2. Current balance of all tokens listed in the organization’s treasury (by treasury we mean funds that are under the Council’s control). 
3. Transaction history for all tokens in the treasury. This will include all transaction types, including contract interactions and token interactions. 


**License** 
1. The API code would be open source, using MIT license or akin to it. 


**Documentation**
1. The API would be documented and provide a clear getting started explanation, and description of end points. 


**Deployment & availability **
1. The API would be deployed on the contractor’s facilities. 
2. The API would be available through a REST interface.  
3. Maintenance. The API provider would be responsible for maintaining the API as required by the platform changes.
