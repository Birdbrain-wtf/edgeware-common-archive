Over the last month or so, I've been working on adding some new features to Substrate's asset pallet. Though the PR is taking too long to merge into substrate, I am instead cloning it directly into Edgeware, as a pallet which we will maintain and add necessary features to. The functionality that differs from Substrate's asset implementation is the ability to allow other modules in our runtime to:
- Create and interact with assets
- Mint assets
- Freeze assets
- Burn assets


The PR can be found here: https://github.com/hicommonwealth/edgeware-node/pull/276

Where is this useful?
- We want a bridge between EVM and native assets. This bridge could manage, as the "owner", a bunch of different assets (namely EVM assets) and allow minting those assets into the native assets system.
- I am building pallets for my own applications that I want to own native assets, being able to mint/burn/freeze assets.
- Future pallets would be able to be built to interact with assets (potentially Treasury reward when we find new use cases)
- For any future bridges that are created trusted/trustless, the developers can utilise this asset functionality: for example for renVM pallet or chainbridge pallet or trustless bridge pallets.


Where is the room for discussion?
- I think this is a good kick-off for the Edgeware EVM <-> Edgeware Native Assets wrapper bridge, where we can provide a way to mint/freeze/burn ERC20 assets from native substrate assets and vice versa.
- Our assets pallet will support all mining/freezing/burning functionality by default. If we want specific tokens to have a subset of this functionality then it needs to be tracked by the bridge itself.
- How should ownership be handled? If the bridge takes ownership of assets being crated _**FROM**_ Edgeware EVM assets, what are the consequences?


Where is there room for more features?
- It would also be nice to have vesting features on the assets so that we can set vesting schedules for certain assets.
- It would be nice to have an NFT pallet integrated in the future with similar functionality, though likely housed in a different module with similar extensible trait impl.
