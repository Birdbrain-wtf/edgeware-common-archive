This is the list of steps I took to verify the proposed "ERUP 3.0" upgrade, named "Tokyo", specifically the "v45" runtime. 

## Verify WASM Binary

First thing I did is check is that the generated WASM checksum of the project matches the uploaded binary.

I did this by checking out the repo at the `v3.2.0` tag and following the `srtool` command line items here, then verifying the content and SHA256 match exactly: [https://github.com/hicommonwealth/edgeware-node/releases/tag/v3.2.0](https://github.com/hicommonwealth/edgeware-node/releases/tag/v3.2.0)

## Attempt "No-op" Dev Upgrade

Next thing to check is that upgrading on an already-up-to-date node has no effect.

1. First ensure that the `srtool` step ran successfully, so you have a generated wasm file at `./target/srtool/release/wbuild/edgeware-runtime/edgeware_runtime.compact.wasm`
2. Then, build the node itself using the setup script `./setup.sh`.
3. Run a development node: `./target/release/edgeware --dev --tmp`
4. Attach to the development node on [https://polkadot.js.org/apps/](https://polkadot.js.org/apps/) by selecting "Local Node" in the sidebar and hitting "Switch". Page should refresh.
5. Attempt an upgrade by going to "Developer → Sudo", hitting "File Upload" on the code input and selecting the built wasm from step 1, and checking "With Weight Override" and setting it to "1". Then hit "Submit Sudo Unchecked". A modal should pop up, showing "Alice" as the account. Hit "Sign and Submit". Eventually the notifications on the top-right should show an extrinsic success.
6. Verify that the chain is still producing blocks, refresh the page and ensure balances etc. are all as expected — nothing should have happened, because I upgraded the runtime to itself.

## Attempt Dev Upgrade

Next I ran a "real" upgrade on a v3.1.0 development node.

1. Ensure the generated wasm file and v3.2.0 binary still exist, from steps 1 and 2 above.
2. Clone a new copy of `edgeware-node` and check out `v3.1.0`.
3. Initialize a chain with the v3.1.0 runtime to a known directory, by running `./target/release/edgeware --dev --base-path <db-dir>` inside the v3.1.0 repo and waiting for it to produce a block or two.
4. "Upgrade" the node to v3.2.0, but maintaining the old runtime, by closing the chain, and running `./target/release/edgeware --dev --base-path <db-dir>` inside the v3.2.0 repo, ensuring that `<db-dir>` is the same as before.
5. Repeat steps 4 and 5 from above, ensuring that in step 4, the polkadot apps site shows "version 41" at the top left, and then "version 45" after the upgrade has gone through. The sidebar will print a lot of API warnings immediately once the upgrade goes through, which should disappear on refresh. The chain itself should print nothing special when the upgrade extrinsic goes through.
6. Verify balances, chain state, etc. until you feel comfortable that the upgrade was successful. To perform txs or query certain modules without error, you may need to add a types JSON in the "Settings → Developer" panel:

    ```tsx
    {
      "Balance2": "u128",
      "ChainId": "u8",
      "DepositNonce": "u64",
      "ResourceId": "[u8; 32]",
      "ProposalStatus": {
        "_enum": [
          "Initiated",
          "Approved",
          "Rejected"
        ]
      },
      "ProposalVotes": {
        "votes_for": "Vec<AccountId>",
        "votes_against": "Vec<AccountId>",
        "staus": "ProposalStatus",
        "expiry": "BlockNumber"
      },
      "AccountInfo": "AccountInfoWithRefCount",
      "Address": "MultiAddress",
      "LookupSource": "MultiAddress"
    }
    ```

    If you wanted to generate this yourself, you could clone the node-types repo here: [https://github.com/hicommonwealth/edgeware-node-types](https://github.com/hicommonwealth/edgeware-node-types) and check out the `tokyo` branch. Build it with `yarn build` then run `yarn print-json dev` to generate the JSON file.

## Attempt Upgrade on Forked Mainnet

Finally, I generated a fork of mainnet and attempted to upgrade that, to ensure that existing chain state upgrades correctly.

1. Generate the runtime wasm file for v3.1.0, in the cloned repo from step 2 above, by running `./scripts/build_only_wasm.sh edgeware-runtime` from its root.
2. Edgeware has a provided script that generates a forked chain spec. In the v3.2.0 repo, open `ts-tests/upgrade-tester/src/scripts/forker.ts` and ensure the `wasmPath` variable points to the file generated in step 1.
    - What this script does is fetch the current state of the chain from a remote endpoint by fetching all storage items, then generates a "forked" chain spec with an Alice sudo key, so you can manually run an upgrade. The script itself is relatively straightforward and may be worth reading to understand the differences between mainnet proper and the forked version used for this test.
3. To generate the actual chain spec, go to the `ts-tests/upgrade-tester` directory and run `yarn` then `HTTP_RPC_ENDPOINT=http://mainnet2.edgewa.re:9933 yarn generate-chainspec` (or select your own mainnet node with `--unsafe-rpc-external --rpc-methods=Unsafe` flags enabled). This will generate an output file `ts-tests/upgrade-tester/src/scripts/forker-data/fork.json`.
4. From the root of the node repo, start a v3.2.0 node with the output chain spec, via `./target/release/edgeware --alice --validator --force-authoring --chain ./ts-tests/upgrade-tester/src/scripts/forker-data/fork.json --base-path <db-dir>` (just ensure that `<db-dir>` does not exist prior to starting the node). Reading the chain spec will take a few minutes, but it should start producing blocks.
5. Load the chain on polkadot apps as above, ensuring that the current data from mainnet appears on the forked chain: should see several proposals of each kind, a council, etc.
6. Run the upgrade via the apps site and ensure it goes through successfully, then verify that the expected data on the apps pages did not change. Note that you may lose the `treasury.approveBounty` council motion, because that call has been moved into a separate `bounties` module in the upgrade — we may want the council to reject this motion before the upgrade goes through, to avoid any lingering storage issues.

That should be it! I recommend reading through the upgrade code, if you have the time and expertise. The `ts-tests` directory also contains some useful testing tools for automating some of the post-upgrade verification, if desired.
